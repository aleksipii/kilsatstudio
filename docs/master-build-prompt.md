# MASTER BUILD PROMPT — Kilsat Studio / StoryMotion Studio

> Reusable target specification. Requirements below describe the intended product; they do not certify that a feature, milestone, license review, hardware test, or export path has been completed. Inspect the repository and attach evidence to each completion claim.

## 1. Mission

You are the lead engineering team responsible for designing, implementing, testing, and delivering **Kilsat Studio**, a professional, screenplay-driven 2D animation desktop application for macOS.

**Product name:** Kilsat Studio  
**Animation engine:** StoryMotion Engine  
**Primary platform:** macOS, Apple Silicon (M1–M-series)  
**Primary language:** Rust  
**GitHub repository:** https://github.com/aleksipii/kilsatstudio

The objective is to build real, functional, maintainable software—not merely documentation, mockups, or architectural proposals.

The application should eventually combine simplified professional capabilities inspired by:

- Adobe Character Animator: character puppets, facial animation, lip synchronization, expressions, and performance controls.
- Adobe Animate: timelines, keyframes, tweens, rigging, and 2D animation.
- Adobe Photoshop: layers, brushes, image editing, masking, and asset preparation.

Its defining feature is a **rule-based English screenplay engine** that converts structured scripts into editable animated scenes, with local English speech generated by the approved Hugging Face **hexgrad/Kokoro-82M** model and synchronized character mouth animation. Offline speech is a core product workstream, not an optional future cloud feature.

The software must be capable of generating animation from a screenplay, while allowing artists to override, refine, and edit the generated result.

### Agent 6 — Audio, Kokoro TTS, and Lip-Sync Engineer

**Mission:** Build a professional, offline-first dialogue and voice animation system powered by Kokoro-82M.

**Primary model:** [hexgrad/Kokoro-82M](https://huggingface.co/hexgrad/Kokoro-82M). **Provider:** Hugging Face. **Primary language:** English. **Execution:** local inference on macOS, prioritizing Apple Silicon compatibility and testing CPU execution first. No paid cloud API is required.

**Responsibilities:**

- Convert MotionScript dialogue into natural-sounding speech and preserve the generated WAV as an audio asset.
- Support character voice presets, language settings, speed, voice previews, regeneration, duration display, and manual placement/trimming.
- Represent speaking style and emotion requests honestly. Do not imply Kokoro supports arbitrary acoustic emotion conditioning; reject unsupported parameters or show their documented fallback. Facial emotion can still drive animation independently.
- Cache synthesis by content and avoid unnecessary regeneration.
- Place speech and mouth animation on the same deterministic timeline used by preview and export.
- Implement a separate alignment stage, timed phoneme-to-viseme mapping, editable timing, and mouth animation.
- Provide waveform previews, audio import, playback, mixing, and synchronized export integration.
- Keep inference, model loading, alignment, and encoding off the UI event loop using bounded jobs with progress, cancellation, and recoverable errors.
- Permit explicit user-provided voice audio when inference is unavailable. Never fabricate speech or silently call an online service.

**Components and ownership:**

```text
crates/
├── motion-audio/       # WAV assets, waveform envelopes, playback/mixing and sample placement
├── motion-tts/         # Provider contract, synthesis errors/results, content-addressed cache
├── motion-lipsync/     # Alignment contracts/provenance, timed phonemes, viseme evaluation
└── motion-voice/       # Character voice configuration and dialogue job/timeline orchestration
services/
└── kokoro-runtime/     # Replaceable local inference sidecar, protocol and runtime tests
```

Keep the Rust application independent of inference implementation through a clean provider boundary:

```rust
pub trait SpeechProvider {
    fn synthesize(
        &self,
        request: SpeechRequest,
    ) -> Result<SpeechResult, SpeechError>;
}
```

Define validated, serializable request/result types carrying text, preset, language, speed, model revision and relevant synthesis parameters; audio format, sample rate/count, duration and provenance; and actionable typed errors. The synchronous provider method runs on a background worker, never on the desktop UI thread. Define sidecar protocol versioning, bounded input/output, timeouts, cancellation, process cleanup, and structured errors without coupling the UI to Python internals.

**Backend decision:** Investigate Python Kokoro, ONNX Runtime, and Core ML options against official model and backend documentation before choosing or changing the backend. A Python sidecar is acceptable for the first reliable functional implementation. Keep replacement by a native Rust-compatible backend possible without rewriting MotionScript or the editor. Establish a repeatable macOS CPU WAV synthesis test before pursuing acceleration. Do not claim native Rust inference, Metal, MPS, Core ML acceleration, or Apple Silicon runtime compatibility until the actual execution path is verified on appropriate hardware. Document backend tradeoffs and exact tested versions.

**Offline assets, consent and licenses:** Obtain appropriate user consent before downloading model weights, voice packs, language data, or aligner models. Keep large assets outside Git in a user-controlled application data/cache location; pin exact revisions and verify hashes. Separate installation/provisioning from offline synthesis, and test with networking disabled after provisioning. Record the model, voice, phonemizer, runtime and dependency licenses, notices and redistribution obligations; an approved model is not a completed dependency audit. Do not bundle unverified assets.

**Cache:** Use a stable content hash over text, preset, exact model and voice revisions, language settings, speed, all output-affecting synthesis parameters, backend/protocol identity and relevant runtime/environment identity. Persist metadata and WAV atomically, validate cache integrity, handle concurrent identical requests, invalidate corrupt or incompatible entries, and provide explicit regeneration. Cache alignment separately using the audio hash, transcript, aligner version/configuration and manual edits.

**Alignment:** Kokoro speech output and phoneme sequences must not be assumed to include accurate phoneme timestamps. Evaluate a separate forced aligner and other timing methods; record whether timings are forced-aligned, manually authored or estimated. Heuristic duration allocation is a fallback, not validated forced alignment. Validate finite monotonic intervals, audio bounds, silence and word/phoneme references. Measure timing error against annotated real audio and assess mouth synchronization perceptually across multiple voices, speaking speeds, pauses and utterance lengths. Document the test corpus, method, measured quality and limitations. Preserve imported alignment and manual corrections.

**Rhubarb Lip Sync option:** Rhubarb Lip Sync (an open-source command-line tool by Daniel Wolf) is a candidate offline mouth-timing backend. It reads a WAV file and, optionally, the known dialogue text, and outputs timed mouth shapes (A–F plus optional G, H and X for rest) as TSV, XML or JSON. Its recognizer is PocketSphinx-based, not a generative model, and it needs no cloud service. Consider it as an alternative or complement to a phoneme forced aligner:

- Run it as an explicit, user-configured external executable, like FFmpeg: a validated path, a bounded background job with timeout, cancellation and progress, and an actionable error when it is missing. Never run it on the UI event loop, and never download it without user consent.
- Pass the dialogue transcript through its dialog-file option when available, since that usually improves recognition. Record the exact Rhubarb version, recognizer mode and options in the alignment provenance. Its output is estimated mouth timing; do not label it forced-aligned or validated quality.
- Rhubarb emits mouth shapes, not phonemes. Map its shapes to `motion-lipsync` visemes through a documented, tested table, or extend the alignment model with a distinct mouth-shape source, rather than inventing phonemes. Validate monotonic finite intervals within the audio bounds.
- Cache results under the exact PCM hash, transcript, Rhubarb version and options, and preserve manual corrections, consistent with the alignment cache rules above.
- Verify the license of the exact release and of its bundled components and models before bundling or redistributing it. Until then, treat it as a user-installed tool.
- Measure its timing error against the same annotated real-audio corpus as other aligners, and assess mouth synchronization perceptually, before describing its mouth timing as validated. English is the expected first language; check other languages explicitly.

**Synchronization:** Use one audio sample clock for dialogue placement, mouth evaluation and export; define conversions to scene time and frame indices explicitly. Handle seeks, pause/resume, offsets, trim, scene boundaries, overlaps and cancellation consistently. Preview device playback should follow the observed playback position rather than an unrelated wall timer. Use deterministic sample placement and the same mix for export. Do not equate a waveform array, JSON manifest or WAV export with a completed waveform UI or synchronized video export.

## 6. Core Product Architecture

The primary data pipeline is:

**MotionScript → Parser → Validator → Compiler → Animation Timeline → Scene Evaluation → Renderer → Preview / Export**

Requirements:

- Frame-accurate timing.
- Deterministic animation evaluation.
- Clear separation between document state and evaluated frame state.
- Editable animation events.
- Stable character and scene identifiers.
- Serializable project data.
- Versioned project format.
- No dependency on network services for core functionality.

The dialogue branch is:

**MotionScript dialogue → background speech provider → local Kokoro → WAV asset/cache → separate speech alignment → timed phonemes/visemes → character mouth animation → synchronized playback and export.**

Connect this branch to the compiled animation timeline through `motion-voice`; keep audio assets, alignment data and project references versioned and editable. Generated duration must be available to timing validation; diagnose speech exceeding scene bounds and define overlap behavior rather than silently stretching or truncating scenes. A text or voice edit invalidates affected synthesis/alignment jobs and assets without changing unrelated dialogue.

The same scene evaluation engine should power interactive previews and offline exports.

Avoid maintaining separate animation behavior for preview and export.

## 7. MotionScript Language

The initial screenplay format should be English-language, structured YAML.

Example:

```yaml
project:
  title: "Hello Emma"
  fps: 24
  width: 1920
  height: 1080

characters:
  EMMA:
    asset: "characters/emma"
    default_pose: "idle"
    voice:
      provider: kokoro
      preset: af_heart
      language: en-us
      speed: 1.0

  ALEX:
    asset: "characters/alex"
    voice:
      provider: kokoro
      preset: am_michael
      language: en-us
      speed: 1.0

scenes:
  - id: intro
    duration: 12.0
    background: "studio"

    events:
      - type: move
        at: 0.0
        actor: EMMA
        x: 400
        y: 700
        duration: 2.0

      - type: emotion
        at: 2.0
        actor: EMMA
        value: happy

      - type: gesture
        at: 2.5
        actor: EMMA
        value: wave
        duration: 1.0

      - type: speak
        at: 3.0
        actor: EMMA
        text: "Hello Alex! Welcome to Kilsat Studio."
        emotion: happy

      - type: speak
        at: 7.0
        actor: ALEX
        text: "This is incredible!"
        emotion: surprised
```

Build a strict, documented schema. Validate voice provider/preset/language compatibility, nonempty dialogue, finite positive supported speed, finite nonnegative event times, actor references and scene bounds. Keep voice configuration backward compatible with existing scripts through documented defaults or explicit diagnostics. Dialogue emotion is animation metadata unless a tested provider capability supports acoustic conditioning. Provide a documented explicit imported-audio path with audio reference, transcript, timing offset and alignment provenance; do not invent schema fields without implementing and testing them.

For Milestone 1, it is acceptable to support only movement, basic expressions, and dialogue text. Unsupported commands must produce clear diagnostics rather than silently failing.

The language should eventually support:

- Multiple characters.
- Multiple scenes.
- Dialogue.
- Emotions.
- Gestures.
- Body movement.
- Camera movement.
- Scene transitions.
- Background changes.
- Audio cues.
- Timing rules.
- Animation presets.
- Conditional or reusable rules.

Do not add complex language features before the basic compiler is reliable.
